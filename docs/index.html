Magic Mouse 2024 (v3) Windows driver — scroll fix for PID 0323

Apple ships no Windows driver for the 2024 USB-C Magic Mouse, Bluetooth PID 0323 — that ID is absent from the Boot Camp INF. This project is a free, MIT-licensed fix for two-finger scroll on Windows 10 and Windows 11, and it now offers two routes: register Apple's own unmodified signed driver (no Windows Test Mode, works on v1, v2 and v3), or install this project's KMDF filter driver (PID 0323 only, tunable scroll, Test Mode required). You install one, not both. The Magic Tray (Windows app) detects which route a machine is using and shows battery percentage in the tray.

Does Apple make a Windows driver for the 2024 Magic Mouse?

No. Apple's Boot Camp driver package contains no entry for PID 0323, so Windows loads only its generic HID mouse stack for the 2024 Magic Mouse. Clicking and cursor movement work out of the box, but nothing from Apple teaches Windows how to keep the touch-surface scroll collection alive.

Installing Apple's Boot Camp software does not rescue the older mice either: Apple's installer refuses to run on non-Apple hardware, and even when applewirelessmouse.sys is present on disk, Windows will not attach it to the mouse until something registers the driver as a lower filter on the device. That registration is exactly what this project's Apple-driver installer does — the approach sbagirici proved on Magic Mouse v1 and v2.

Why does Magic Mouse scroll stop working on Windows 11 after a Bluetooth reconnect?

Because Windows collapses the mouse's HID collections. After a Bluetooth idle disconnect, DeviceSetupManager (DSM) runs a property synchronisation pass, and on reconnect the device can come back in a reduced form — this project calls it Mode A → Mode B. Mode A exposes the full collection set including the touch-surface report; Mode B exposes only the plain mouse collection. The cursor still moves and clicks still register, so the mouse looks healthy, but two-finger scroll is gone. It does not self-recover: before this driver, the only ways back were a driver reinstall or re-pairing the mouse.

What does the Magic Mouse v3 Windows driver do?

Both routes are kernel-mode lower filters on the mouse's Bluetooth HID stack, and both end with working two-finger scroll. They get there differently:

  • Apple-driver route (v1-binary-patch/, v1.0.0, production ready) — ships Apple's own applewirelessmouse.sys completely unmodified and registers it: the binary is copied to System32\drivers, an applewirelessmouse kernel service is created, the driver is added to the device's LowerFilters, and the Bluetooth HID device is restarted. Because the binary is untouched and no catalog is installed, no Windows Test Mode is required. Scroll feel is Apple's own Mac-style translation, and sensitivity is fixed. Supports 0x030D, 0x0269, 0x0310 and 0x0323.
  • KMDF driver (v2-kmdf-driver/, 2.0.4.3) — a lower-filter driver written from scratch in C against the public Windows Driver Kit. It contains no Apple code and does not need Apple's binary; it generates scroll directly from the touch surface as HID Wheel and AC Pan. Scroll sensitivity is tunable with the ScrollStep registry value, and it re-arms multitouch automatically after a Bluetooth reconnect and after a reboot. It is self-signed, so it requires Windows Test Mode, and it supports 0x0323 only. This is the package the Magic Tray (Windows app) installs via v2-kmdf-driver/Install-KMDF.cmd.

Install one route, not both — they attach to the same Bluetooth HID stack. Either route restores scroll; neither changes button mapping, gestures, or pointer acceleration.

Which Magic Mouse do I have?

Check the Bluetooth product ID: in Windows, open Device Manager → Human Interface Devices → Apple Magic Mouse → Properties → Details → Hardware Ids, and read the PID_ value. PID_0323 can use either route; the older IDs need the Apple-driver route.

If your Hardware Ids show PID_0269, PID_030D or PID_0310, use the Apple-driver route: pass -TargetPid to the PowerShell installer, or just let Install.cmd detect the paired mouse. The KMDF driver will not help you — it is 0x0323 only.

How do I see Magic Mouse battery percentage on Windows?

Use the Magic Tray app — neither driver reads battery itself. The 2024 Magic Mouse reports its charge on HID Input report 0x90, collection COL02, and parsing that report is userspace work done by the Magic Tray (Windows app), which puts the percentage in the Windows notification area. How it gets the number depends on the route: with the KMDF driver it reads report 0x90 directly, and on the Apple-driver route it performs a brief, temporary Mode A to Mode B flip on the device and then flips it back.

How do I install the Magic Mouse 2024 (v3) Windows driver?

It depends which route you pick. For the Apple-driver route, turn Fast Startup off (powercfg /h off from an elevated prompt, then reboot), download the repo and double-click v1-binary-patch/Install.cmd: it asks for Administrator itself, uses the bundled unmodified Apple driver, needs no PowerShell window and no execution-policy change, and a reboot finishes the job. No Test Mode, and Secure Boot and memory integrity can stay on.

For the KMDF driver, enable Windows Test Mode first and then run Setup-Community.cmd: that package is self-signed today, so Windows refuses to load it while signature enforcement is on. Test Mode is required for the KMDF route — it has to persist across reboots, so a one-shot disabled-enforcement boot is not enough — until the project can pay for an EV certificate and Microsoft attestation signing.

The full sequence for both routes, including how to undo either one, is on how to install the Magic Mouse v3 driver on Windows 11.

Is this driver free, and how does it compare to Magic Utilities?

It is free and MIT licensed, with no subscription. Magic Utilities is paid software sold on a subscription; this project is not, and nothing here expires or stops scrolling when a licence lapses. It is maintained by Revive Business Solutions / Lesley Murfin and is not affiliated with Apple.

Signing is the one thing money buys — for the KMDF driver. That driver is self-signed today and the goal is an EV certificate plus Microsoft attestation signing, funded through Stripe rather than GitHub Sponsors — see the driver signing funding page. The Apple-driver route sidesteps the problem entirely because it redistributes Apple's own signed binary without touching a byte of it.
