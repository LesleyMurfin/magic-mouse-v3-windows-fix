Magic Mouse battery percentage on Windows 11

The free Magic Tray (Windows app) puts Magic Mouse battery percentage next to the Windows clock. The shipped Apple-driver route does not read battery itself — Magic Tray does it in userspace with a brief, temporary Mode A to Mode B flip, then flips the device back. The KMDF route is development work only and is not shipped on this branch.

Which devices have a characterised battery report?

Magic Tray reads Input report 0x90 on collection COL02. Only the 2024 mouse’s collection layout has been mapped so far — older models use a different HID descriptor structure and are tracked, not yet supported, on issue 22.

How do I check my Magic Mouse battery on Windows?

  1. 1

    Install Magic Tray

    Get the free Magic Tray (Windows app). It is a system-tray utility, not a driver, and not a physical desk accessory.

  2. 2

    Look next to the clock

    The battery percentage for the Apple-driver route appears automatically beside the Windows clock — no setup step beyond installing.

  3. 3

    What happens behind the scenes

    Magic Tray briefly flips the device from Mode A to Mode B, takes the charge reading on report 0x90, then flips it back. The flip is temporary by design.

Magic Tray is Windows software — a system-tray utility for Apple mice on Windows. It is not a desk accessory, a keyboard stand, or a 3D-printed or wooden tray, despite what a shopping search suggests. Source: the Magic Tray (Windows app) repo on GitHub.

Why does the scroll driver matter for a battery read?

The battery report arrives on a HID collection, and this mouse can lose its collections. After a Bluetooth idle disconnect, DeviceSetupManager property synchronization can collapse the mouse’s HID collections — Mode A → Mode B — leaving a plain mouse with a working cursor and no touch surface. When the collection layout collapses, the collection carrying report 0x90 is not there to read either, so a battery reading can go stale or stop along with scroll.

Common questions

Why does Windows 11 not show the battery level itself?

Because the paths Windows normally uses are not dependable for this mouse. Windows Settings and WMI are not reliable sources for Magic Mouse 2024 battery state, and Feature report 0x47 is not where the level lives. The number is in an Input report the mouse sends on a specific collection, so something has to be listening on that collection and decoding it — which is what Magic Tray does.

Does this work on Magic Mouse 1 or Magic Mouse 2?

Scroll, yes: v1 (0x030D), v2 (0x0269) and v2-alt (0x0310) are supported by the Apple-driver route. Battery on those models is a different story and this project does not claim it either way yet — they use different HID descriptor structures from the 2024 mouse, so the collection that carries report 0x90 on 0x0323 has not been mapped on them and the battery path is not yet characterised (issue 22). For what Magic Tray supports, see the Magic Tray (Windows app) site.

Does the KMDF route show battery too?

Not on this branch. The KMDF route is development documentation only: this branch contains its README/status material, not an installable package, compiled .sys, or installer, so there is no current battery path to document for it.

Protocol detail: reports, collections and what Magic Tray does not use

The 2024 Magic Mouse (PID 0x0323) sends its charge state on HID Input report 0x90, on the collection referred to here as COL02. Magic Tray listens on that collection and decodes the report; it is not a kernel driver and does not modify the device.

Feature report 0x47 is not the battery source, despite being a plausible-looking candidate in the descriptor — do not decode it as charge level. Windows Settings and WMI are not reliable battery sources for this mouse either.

The shipped kernel filter (the Apple-driver route) restores and protects two-finger scroll only; neither it nor the unreleased KMDF route reports battery. Full notes: HID research notes, including Input report 0x90.
